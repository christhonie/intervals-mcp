= Runbook — Rotating Secrets
:description: How to rotate the OAuth client secret and the Intervals.icu API key for the deployed MCP server.
:keywords: runbook, oauth, secret, rotation, security, kubernetes

This runbook covers rotating the two credentials the server holds in the
`intervals-mcp-secrets` Kubernetes Secret (namespace `mcp`):

* `OAUTH_CLIENT_SECRET` — the pre-shared secret the connector (claude.ai) uses to
  authenticate to this server's OAuth `/token` endpoint.
* `INTERVALS_API_KEY` — the upstream Intervals.icu personal API key.

[NOTE]
====
Neither value is ever stored in git — both are created out-of-band (see
`k8s/secret.template.yaml`). Rotation is **defense-in-depth / hygiene**, not a
response to a repo leak. Rotate on a schedule, on suspected exposure, or when
offboarding a device that held the value.
====

== How the OAuth client secret is used

The server is its own OAuth 2.1 authorization server with a *single* pre-registered
client (no dynamic client registration). See `src/http-server.ts` and
`src/oauth-provider.ts`.

* The auth method is `client_secret_post`: claude.ai sends `client_id` +
  `client_secret` in the body of every `/token` call — both the initial
  authorization-code exchange **and every refresh**.
* The bearer access tokens used at `/mcp` are opaque tokens minted by the server
  and validated against the OAuth store (Redis or in-memory). They do **not**
  depend on the client secret.

*Consequence:* rotating the secret does not invalidate live access tokens (they
age out at their TTL, ≤1 hour), but the next token **refresh** from claude.ai
presents the old secret and is rejected — so the connector breaks until claude.ai's
copy of the secret is updated too. This minimal provider has no dual-secret overlap,
so expect one brief reconnect rather than a seamless rotation.

== Rotate `OAUTH_CLIENT_SECRET`

. *Generate a new secret*
+
[source,bash]
----
NEW_SECRET=$(openssl rand -hex 32)
----

. *Patch the Kubernetes Secret.* This changes one value, not the key schema, so a
  merge-patch is safe (the delete-and-recreate caveat in `secret.template.yaml`
  applies only to *removing* keys):
+
[source,bash]
----
export KUBECONFIG=<your-kubeconfig>
kubectl -n mcp patch secret intervals-mcp-secrets --type merge \
  -p "{\"stringData\":{\"OAUTH_CLIENT_SECRET\":\"$NEW_SECRET\"}}"
----

. *Restart the pod.* `envFrom: secretRef` is injected at container start, so a
  Secret change is **not** picked up until a restart:
+
[source,bash]
----
kubectl -n mcp rollout restart deployment/intervals-mcp
kubectl -n mcp rollout status deployment/intervals-mcp
----

. *Update the claude.ai connector.* Edit the `Intervals_MCP` custom connector,
  replace the stored client secret with the new value, and re-authenticate (start
  a new conversation / reconnect). Until this step, the connector fails on its next
  refresh.

. *(Optional) flush stale OAuth state.* To force a clean slate rather than letting
  old tokens age out, clear the server's store keys (prefix `intervals-mcp:oauth`)
  in Redis, or `rollout restart` again when running in-memory.

[TIP]
====
`OAUTH_CLIENT_ID` can stay the same — only the secret needs to change. Rotate the
id too only if you want; it follows the same flow.
====

== Rotate `INTERVALS_API_KEY`

This is the genuinely sensitive upstream credential. Same mechanics:

. Generate a new personal API key in the Intervals.icu account settings (and revoke
  the old one once the new one is confirmed working).
. Patch the Secret and restart:
+
[source,bash]
----
kubectl -n mcp patch secret intervals-mcp-secrets --type merge \
  -p '{"stringData":{"INTERVALS_API_KEY":"<new-key>"}}'
kubectl -n mcp rollout restart deployment/intervals-mcp
----
. No claude.ai-side change is needed — the API key is used only server→Intervals.icu.

== Verify

* `kubectl -n mcp rollout status deployment/intervals-mcp` reports the new
  ReplicaSet available.
* `GET /healthz` returns `{"status":"ok"}`.
* In claude.ai, a tool call (e.g. `get_athlete_profile`) succeeds after reconnect —
  confirming both the new OAuth secret (connector auth) and, if rotated, the new
  Intervals.icu key (upstream auth).
