== Decisions

[#adr-001]
=== ADR-001: Build from scratch in TypeScript (do not fork hhopke)

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
The handover proposed evaluating `hhopke/intervals-icu-mcp` (Python/FastMCP, 50+ tools) as a fork base.
However, claude.ai remote connectors require the server to be an OAuth 2.1 + PKCE authorization server — the connector UI has no bearer-token/header field.
The community servers implement no auth on their HTTP transport.
The reusable OAuth layer already exists, in TypeScript, in the operator's `fatsecret-mcp` and `hevy-mcp` deployments.

Decision::
Build a new TypeScript server following the `fatsecret-mcp` / `hevy-mcp` pattern, reusing the OAuth provider and HTTP transport almost verbatim.
Use `hhopke/intervals-icu-mcp` as an endpoint and naming reference only.

Consequences::
+
* Positive: the hard, claude.ai-specific work (OAuth) is reused and proven; only ~16 purpose-built tools are needed, all carrying coaching logic we would have had to add to a fork anyway; one language across the operator's MCP fleet.
* Negative: we forgo hhopke's breadth of generic tools (out of scope) and reimplement endpoint wrappers.

Alternatives considered::
Fork hhopke and add a Python OAuth layer — rejected: diverges from the proven TypeScript deployments and leaves the hardest work unbuilt in a second language.

=== ADR-002: Host on Kubernetes (not Cloudflare Workers)

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
Two hosting targets were considered: the existing k8s cluster (mcp namespace, ArgoCD/cert-manager/nginx) and Cloudflare Workers (native remote-MCP + OAuth support).

Decision::
Deploy to Kubernetes using the same pattern as `fatsecret-mcp` / `hevy-mcp`, at `https://icu-mcp.christhonie.co.za/mcp`.

Consequences::
+
* Positive: fully covered by the `remote-mcp-wrap` skill and two working precedents; no new deployment playbook.
* Negative: more moving parts than a Worker; single-replica in-memory sessions reset on rollout (acceptable for single-user).

Alternatives considered::
Cloudflare Workers — arguably cleaner OAuth, but net-new territory with no existing Workers MCP and no skill coverage.

[#adr-003]
=== ADR-003: Hand-written API client (not generated)

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
The Intervals.icu OpenAPI spec (115 paths, 108 schemas) is available but uses Spring content-negotiation path suffixes (`{format}` / `{ext}`) that do not map cleanly onto codegen clients.
The server touches only ~10 endpoints.

Decision::
Write a small typed client by hand over the global `fetch`, and commit `openapi-spec.json` as the field-name source of truth.

Consequences::
+
* Positive: no codegen friction; response projections expose exactly the coaching fields; descriptive error surfacing is straightforward.
* Negative: endpoint additions are manual; types are hand-maintained rather than generated.

Alternatives considered::
Kubb (as in `hevy-mcp`) or `openapi-fetch` + generated types (as in `fatsecret-mcp`) — rejected due to the path-suffix friction for a small endpoint surface.

=== ADR-005: Replace TARGET events via delete-then-recreate

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
`push_weekly_target` originally updated an existing target with `PUT /events/{eventId}`.
Testing (2026-06-02) showed the Intervals.icu API rejects any PUT to a Plan Builder TARGET event with `HTTP 422 "Cannot change TARGET date"` — even when the `start_date_local` is unchanged.
`DELETE /events/{eventId}` was confirmed permitted on a TARGET event (tested against event 113776607: `200`, then GET → `404`).

Decision::
When `event_id` is supplied, replace the target by delete-then-recreate: DELETE the existing event, then POST a new TARGET with the same `week_start`, `end_date_local = week_start + 7` (exclusive), `load_target`, and `phase_name`.
The DELETE tolerates `404` so the operation is idempotent. Creation (no `event_id`) is unchanged.
Two further requirements were found while implementing this: TARGET creation requires `type` (the API returns `422 "type is required for category TARGET"`; set to `"Ride"`), and event POSTs require a full ISO datetime for `start_date_local` / `end_date_local` (date-only is rejected). A `toDateTime` helper now normalises these for `push_weekly_target`, `push_workout`, and `push_note`.

Consequences::
+
* Positive: weekly-target recalibration works against Plan Builder targets; single tool retained (no separate `replace_weekly_target`).
* Negative: the recreated event gets a new id, and Plan Builder linkage / non-supplied fields (e.g. `time_target`, `distance_target`) are not carried over. Plan Builder places TARGETs with `end_date_local = start + 1 day`; recreated targets use the spec's `+ 7 days` (exclusive) convention.

[#adr-006]
=== ADR-006: Per-sport targets as separate TARGET events per week

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
Phase 4 wanted per-sport weekly targets (load / duration / notes per sport). Investigation found the API has no nested sport-target field on a TARGET event, and TARGET events reject `PUT`. A live probe confirmed multiple TARGET events can coexist in one week, one per `type`, each carrying `load_target`, `time_target`, `distance_target`, and `description` (the free-text note).

Decision::
Model per-sport targets as separate `category: TARGET` events per sport per week. `push_sport_targets(week_start, sport_targets[])` replaces all of a week's TARGET events (delete-then-recreate) with one per supplied sport. `get_weekly_targets` groups by week and nests `sport_targets[]`, summing `load_target`.

Consequences::
+
* Positive: per-sport compliance rings render correctly in the Plan Builder UI (verified on the 2026-06-01 pilot); notes carry phase context.
* Negative: `phase_name` is `null` on restructured weeks (event name = sport type); phase lives in notes. The UI auto-derives a Ride distance from duration even when `distance_target` is unset.

Rollout:: Pilot week 2026-06-01 applied and UI-verified. The remaining 27 weeks are delegated to a separate session, driven by the value table in the handover document.

[#adr-007]
=== ADR-007: Optional Redis-backed OAuth state (template)

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
Sessions and OAuth tokens were in-memory per pod, so every rollout forced claude.ai to re-authenticate / re-initialise — surfacing as the opaque "Error occurred during tool execution" (see BUG-01). The cluster has a Redis instance available.

Decision::
Persist only the **OAuth layer** in Redis (the part that forces re-authentication), via a pluggable `OAuthStore` (`src/oauth-store.ts`): in-memory by default, Redis when `REDIS_URL` is set. The MCP transport/session stays in-memory (a live transport cannot be serialised; making it durable would need stateless mode or sticky sessions — out of scope). Redis errors degrade gracefully to in-memory behaviour. Built as a generic template for the sibling MCP servers.

Consequences::
+
* Positive: tokens survive rollouts — no forced re-auth after a deploy. Generic and reusable (`createOAuthStore("<app>:oauth")`). Graceful degradation keeps the server up if Redis is down.
* Negative: a new optional dependency (Redis) and `ioredis`. The MCP session id is still unknown to a new pod after a rollout, so the client must re-initialise a session (expected to be transparent while the token is valid). One reconnect is still required immediately after first enabling Redis, because the pre-existing token predates the Redis store.

Scope:: Persists only the OAuth layer (codes/tokens), not the MCP session transport. Activated per deployment by setting `REDIS_URL`; built as a reusable template for the sibling MCP servers (`fatsecret-mcp`, `hevy-mcp`).

[#adr-008]
=== ADR-008: `push_sport_targets` empty array clears a week

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
Phase 5 needed to remove all TARGET events from certain weeks (the 2026-05-04 null-load placeholder; the 2026-08-03 / 2026-08-10 UK-travel weeks) without recreating any. The original schema required `sport_targets` to have at least one entry (`.min(1)`), so there was no way to express "clear this week" through the tool.

Decision::
Relax the schema to allow an empty `sport_targets` array, meaning "delete all of the week's `category: TARGET` events and recreate none". NOTE events in the week are never touched (the delete step filters to `category: TARGET`). The non-empty behaviour (one TARGET per sport) is unchanged.

Consequences::
+
* Positive: one reusable primitive for travel / no-target weeks and stray-placeholder cleanup; idempotent.
* Negative: an empty array is a slightly implicit way to express "clear" — mitigated by the tool description.

Alternatives considered::
A separate `clear_weekly_targets` tool — rejected as redundant surface area; the empty-array overload reuses the existing delete-then-recreate path.

=== ADR-009: WeightTraining load already feeds the PMC — no separate field, accept the display split

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
Phase 6 reported that manually-written `icu_training_load` on no-HR `WeightTraining` activities was not counted in fitness, and hypothesised a separate load field / flag was needed, with a backfill of 11 activities. Investigation (OpenAPI `Activity` schema + live probes) found no separate manual-load field or flag; `icu_training_load` is the sole field, it persists across edits, and all 11 historical activities already carried it. A PMC reconstruction from the ATL recurrence showed implied daily load tracks the activity sum *including* gym — i.e. gym load already feeds CTL/ATL at full weight.

Decision::
Treat Phase 6 as resolved with no code change and no backfill. The activity-details screen and the PMC are correct. The remaining `0` on the calendar day tile and the Plan Builder compliance ring come from a separate Intervals computation path (HR/power-derived load, `0` without HR) that does not honour the manual field; this display split is accepted (Path C). Coaching reads true loads from `icu_training_load` (PMC, and `get_weekly_targets` per-sport `completed_load`), not the UI display.

Consequences::
+
* Positive: avoids writing speculative/redundant data; coaching accuracy is already correct.
* Negative: a calendar-tile / compliance-ring display discrepancy remained at the time of writing (since resolved — see Update).

Update (2026-06-03)::
The display split was **resolved**, not merely accepted. Setting the WeightTraining Activity-Types fitness contribution to 100% (`ctlFactor`/`atlFactor = 1`, via the ADR-011 tool) fixed it: the athlete confirmed the gym session's calendar tile now shows `Load 41` (no brackets) and the Plan Builder weekly compliance ring adds to the weekly total and %. Intervals auto-re-analysed historical sessions. The earlier conclusion that the contribution factor "does not drive" that display path was wrong — it does. Path A (HR strap) is therefore not required.

[#adr-010]
=== ADR-010: `update_sport_settings` — athlete sport-settings write with preview→confirm

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
Phase 7 required writing FTP / LTHR / max HR / resting HR / power & HR zones (the immediate need: revise the Ride HR zones for a high-HR phenotype). The handover's stated endpoint `PUT /athlete/{id}/settings/{sport}` does not exist.

Decision::
Add `update_sport_settings`. Sport-level fields are written to `PUT /api/v1/athlete/{id}/sport-settings/{id}`, where the record is located by its `types` list; `resting_hr` is athlete-level (`icu_resting_hr`) and written via `PUT /api/v1/athlete/{id}`. Both are partial merges (verified). The tool is **preview-by-default**: without `confirm: true` it returns a current→proposed diff and writes nothing. Validation: zone arrays must be 7 strictly-ascending values; HR-zone top must not exceed `max_hr`.

Consequences::
+
* Positive: programmatic zone/threshold changes with a safety guard; only supplied fields change.
* Negative: power zones are stored as percentages of FTP on this athlete's record (contradicting the handover's "watts" note) — callers must match the record's existing array format when changing power zones.

[#adr-011]
=== ADR-011: `update_activity_type` — fitness-contribution config via `icu_type_settings`

:adr-status: Accepted
:adr-date: 2026-06-02

Status:: Accepted

Context::
Phase 8 asked to expose the per-activity-type "fitness contribution" so WeightTraining/Yoga can be tuned. The config is the athlete-level `icu_type_settings` array (`{type, ctlFactor, atlFactor}`, 1.0 = 100%), written via `PUT /api/v1/athlete/{id}` — not the `athlete-types` endpoint the handover guessed.

Decision::
Add `update_activity_type(type, ctl_factor?, atl_factor?, confirm?)`, preview-by-default, that reads the full `icu_type_settings` array, merges the entry for the type, and writes the whole array back (other types preserved). Expose the real fields (`ctlFactor`/`atlFactor`) rather than a lossy percentage abstraction.

Consequences::
+
* Positive: the config is controllable as requested; merge preserves other type overrides.
* Outcome (2026-06-03): setting WeightTraining to `ctlFactor/atlFactor = 1` (100%) **fixed the calendar-tile and compliance-ring display** (athlete-confirmed; Intervals auto-re-analysed history). Yoga set to `0` (it carries null load). This corrects the earlier expectation that the factor would not affect that display path (see ADR-009 Update).

[#adr-012]
=== ADR-012: Demote IcuSync to secondary/backup (do not retire yet)

:adr-status: Accepted
:adr-date: 2026-06-03

Status:: Accepted

Context::
The custom MCP now covers the coaching workflow (20 tools, Phases 1–8) and is the primary interface. The original plan was to retire IcuSync once validated. In practice the custom MCP is still young and bugs are still being found.

Decision::
Keep IcuSync connected but **demote it to a secondary/backup tool** rather than retiring it. The custom MCP is primary; IcuSync remains available as a fallback while the custom server burns in and bugs are weeded out. Revisit retirement once the custom MCP has run cleanly in primary use for a sustained period.

Consequences::
+
* Positive: a safety net remains if a custom-MCP bug blocks a coaching task; no rush to retire.
* Negative: two overlapping connectors coexist; the coaching agent must treat the custom MCP as authoritative and IcuSync as backup to avoid divergence.

[#adr-013]
=== ADR-013: `get_activity_streams` — query param is `types`, response is an array

:adr-status: Accepted
:adr-date: 2026-06-13

Status:: Accepted

Context::
Phase 10 adds `get_activity_streams` to expose raw per-second time-series (the SmO₂ + DFA α1 baselining programme needs per-second resolution the interval-aggregate tools cannot provide). The handover spec described the endpoint as `GET /api/v1/activity/{id}/streams?streams=smo2,…` returning "an object keyed by stream name". The committed `openapi-spec.json` (the field-name source of truth — ADR-003) disagrees on two points: the query parameter is **`types`** (not `streams`), and the 200 response is an **array** of `ActivityStream` objects (`{type, name, data, …}`), not an object keyed by name. The path is `/streams{ext}`; consistent with the existing `getActivity` call we omit the Spring content-negotiation suffix and let the `Accept: application/json` header select JSON. `includeDefaults` defaults to `false`, so only the requested `types` are returned.

Decision::
Trust the OpenAPI spec over the handover prose. The client calls `GET /api/v1/activity/{id}/streams?types=…`; the tool reshapes the returned array into the handover's documented output envelope (`{ activity_id, duration_seconds, sample_rate_hz: 1, streams: { <name>: number[] } }`), keying by the caller's requested stream names (case preserved — `RMSSD` is uppercase) and reporting any unavailable streams under `missing_streams`. `duration_seconds` is the longest returned sample array.

Consequences::
+
* Positive: the keyed-envelope contract the coaching layer expects is preserved, decoupled from the API's array shape; case-sensitive pass-through avoids mismatches on streams like `RMSSD`.
* Risk: not yet live-validated against activity `i156869660` — `types` vs `streams` was decided from the spec, not a live call. Validate post-deploy (confirm `smo2` length == `duration_seconds` 4204) before relying on it for the baselining analysis.

== Validation status

Read tools were validated live against athlete i579914 on 2026-06-02:

* *`get_power_curves`* — RESOLVED. The endpoint works with `type` + date range; the spec's required `f1`/`f2`/`f3` are tolerated absent. Output is projected to standard durations (5s/1min/5min/20min/60min) with watts and W/kg.
* *eFTP* — RESOLVED. Sourced from `wellness.sportInfo[].eftp`, not a top-level field.
* *`get_events` `completed` flag* — RESOLVED. `paired_activity_id` is returned and populated, despite being absent from the documented `EventEx` schema.
* PMC float noise rounded (CTL/ATL 1dp, ramp rate 2dp).

Still open:

* *Write tools* — validate in the Intervals.icu UI; not exercised live to avoid polluting the calendar. Confirm the event `start_date_local` format and the `push_note` week-row round-trip.
* *Environment variable naming* — this build uses `INTERVALS_API_KEY` / `INTERVALS_ATHLETE_ID` (handover original), not hhopke's `_ICU_` infix, since we did not fork.
